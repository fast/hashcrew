# Performance and coverage review — 2026-09-07

## Scope and method

This review covers the four algorithm families, streaming state and `std::io::Write` adapters, public examples, integration and library tests, benchmark cases, and the CI configurations. The core baseline is `c357bb2` (PR #18); the measured core change adds `#[inline]` to `Xxh64::update` and `Xxh64::digest`. The extra streaming cases were present in both sides of the focused comparison.

Environment: Apple M4 Max, 36 GiB memory, macOS 26.6.2, `aarch64-apple-darwin`, Rust 1.98.0 (`88d9e12ae`, LLVM 22.1.8). Cargo's bench profile inherits the repository release configuration: thin LTO and one codegen unit. No `target-cpu=native` or extra `RUSTFLAGS` were set. XXH3 uses the target's NEON support. Comparisons use the locked versions: `twox-hash` 2.1.4, `xxhash-rust` 0.8.18, `cityhasher` 0.1.0, `cityhash-rs` 1.0.1, `murmur3` 0.5.2, and `fnv` 1.0.7.

An initial sweep measured every existing case for 0.05–0.1 seconds. The tables below use three serial runs per case with a 0.1-second minimum and 0.25-second maximum, reporting the median of the three run medians. GB/s means decimal bytes per nanosecond. Inputs are reused in memory, so these are warm-buffer CPU measurements, not file-I/O or cold-memory throughput. Construction and finalization are included in streaming timings. Constant one-shot seeds may allow specialization. CPU scheduling and frequency are uncontrolled; small differences, particularly around 5% or below, should be treated as noise rather than a ranking. The 7-byte-chunk baseline was especially variable.

## Measured XXH64 change

`Xxh64::update` and `digest` lacked the inline hints already used by XXH32. Exposing both bodies to caller optimization improves short messages and repeated small writes without changing the algorithm, state layout, overflow behavior, or adding unsafe code. The upstream `twox-hash` implementation also documents caller inlining as important for streaming performance. The table uses separate three-run measurements before and after the change with otherwise identical streaming cases.

| Bytes / chunk bytes | Before ns | After ns | Latency reduction |
| ------------------- | --------- | -------- | ----------------- |
| (32, 8)             | 15.57     | 12.96    | +16.8%            |
| (241, 17)           | 79.85     | 68.78    | +13.9%            |
| (4096, 7)           | 3999.00   | 2187.00  | +45.3%            |
| (4096, 64)          | 288.80    | 198.90   | +31.1%            |

## Tests and examples

- Replace the I/O test's type-only assertions with one behavioral helper instantiated for all nine streaming variants. It checks empty writes, small writes, digest observations, `flush`, continued `write_all`, and `io::copy` against one-shot results over an input larger than the usual I/O buffer.
- Add an XXH32 library test covering all offsets modulo 16, lengths around 16- and 32-byte boundaries, and direct versus buffered input. Previously the library's XXH32 test only exercised length overflow with one byte, so the CI Miri job did not execute its complete-block `read_unaligned` path. Keeping this test inside the library makes it part of the existing Miri job.
- Keep randomized reference tests, exhaustive two-way partitions, and long boundary cases: they exercise different failure modes. Unit and integration empty-vector checks overlap, but library checks also run in the smaller Miri and no-default-features suites; removing them only for deduplication would reduce those suites.
- Add a runnable `HashMap` example to `Xxh3_64Builder`, complementing the existing complete-input, streaming, and file-hashing examples. The public distinction between raw bytes and Rust's typed `Hash` encoding is already documented. Deterministic builders and full-width `u128` digests are deliberate API choices; no random dependency or truncated 128-bit `Hasher` is added.
- Extend benchmarks with empty one-shot input, short streaming messages, irregular 7- and 17-byte chunks, and multiple chunk sizes for the same 4 KiB input. Add target selection and harness-argument forwarding to `cargo x bench`, and route the README commands through that entry point.

## Next opportunities

1. Profile XXH3 with short streaming writes before changing its kernel. The large-buffer path is already competitive, while repeated buffer handling and finalization remain plausible sources of overhead; the measurements alone do not identify the exact cause. Preserve the validated secret-length invariant when investigating custom-secret paths.
2. Add equivalent custom-secret streaming comparisons with explicitly matched ownership and construction costs. A borrowed secret and an allocating constructor measure different contracts. Add runtime-seed and reusable-builder cases if hash-table construction is a target workload; the current fixed-seed one-shot results cannot answer that question.
3. Run the same matrix on physical x86-64 hosts with default features and explicit AVX2. CI currently compiles the explicit AVX2 target; this review's performance conclusions are limited to Apple AArch64. Cross-target compilation does not establish runtime speed.
4. Extend the full independent-reference integration suite to a `hashcrew` dependency with default features disabled. `cargo x test` currently tests the library separately without default features, but the integration package enables the default `std` feature. Bare-metal/Wasm compile checks and library tests are useful but do not replace the complete conformance suite for scalar dispatch.
5. Consider a development-only direct C/C++ comparison for variants whose Rust reference APIs are missing, particularly seeded CityHash128. Existing seeded CityHash tests check vectors and API relationships, which are narrower than broad independent-reference coverage.

## Validation

`cargo x check` and `cargo x test` passed on Rust 1.98.0 and the Rust 1.85.0 MSRV, including the new I/O helper and builder example. `cargo x bench -- --test` executed every benchmark case once, including empty input. The new XXH32 alignment test passed under `cargo +nightly miri test --package hashcrew --lib --no-default-features --release unaligned_streaming_blocks_match_oneshot` with `MIRIFLAGS=-Zmiri-strict-provenance`. The full repository lint workflow also passed.

## Reproduction and upstream context

```shell
RUSTUP_TOOLCHAIN=stable cargo x bench --bench throughput -- 4096 1048576 --min-time 0.1 --max-time 0.25
RUSTUP_TOOLCHAIN=stable cargo x bench --bench streaming -- --min-time 0.1 --max-time 0.25
RUSTUP_TOOLCHAIN=stable cargo x bench --bench streaming -- xxh64 --min-time 0.1 --max-time 0.25
```

Repeat each command three times without concurrent builds or benchmarks. Use Rust 1.98.0 instead of the moving `stable` alias to reproduce the compiler version. For the before/after comparison, retain the extended benchmark cases and change only the two inline attributes. The measured values are a snapshot, not CI performance thresholds.

The [twox-hash examples](https://github.com/shepmaster/twox-hash#examples) distinguish complete input, streaming, and hash-map use. Its [comparison methodology](https://github.com/shepmaster/twox-hash/blob/main/comparison/README.md) varies chunk sizes and distinguishes C call overhead; its published numbers use different machines and are not mixed into these tables. [xxhash-rust](https://github.com/DoumanAsh/xxhash-rust#hw-acceleration) documents compile-time SIMD selection and separates one-shot from streaming implementations. The [CityHash reference](https://github.com/google/cityhash/blob/master/README) also emphasizes that rankings depend on input size, compiler, and hardware. Source inspection used the locked Rust crate versions listed above.
